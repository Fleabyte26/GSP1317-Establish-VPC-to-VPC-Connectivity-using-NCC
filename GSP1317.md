# GSP1317 - Establish VPC to VPC Connectivity using NCC

## Known lab traps/bugs (read first)

1. The lab leaves five values for you to find and paste by hand: region, the Cloud SQL instance name (blank in the lab's commands), a free IP address, the service attachment URI and the DNS record. Setup and Task 4 detect all of them; nothing to edit.
2. The lab asks you to pick a free IP and warns about "already being used" errors. Here the address is reserved without naming an IP, so Google picks a free one and that error cannot happen.
3. The lab says you will switch between two projects. Every command in it uses one project, the one Cloud Shell opens in. Stay in that project.
4. The lab hardcodes the ping target 10.1.1.2. This tutorial reads the real IP of vm1-vpc1-ncc.
5. Task 5 in the lab is an interactive psql session with a password prompt. Here it runs as two commands from Cloud Shell, no typing inside the VM.
6. Do not run Task 6 (delete) until all four checks are green. Delete removes what the checker looks for.
7. The checker lags: wait 30-60 seconds and click again.

## Setup

```bash
gcloud config get-value project > ~/project
gcloud services enable networkconnectivity.googleapis.com
gcloud config set accessibility/screen_reader false
gcloud compute networks subnets list --filter="name=vpc2-ncc-subnet1" --format="value(region.basename())" > ~/region
gcloud sql instances list --format="value(name)" | head -1 > ~/sqlname
gcloud compute instances list --filter="name=cloudsql-client" --format="value(zone.basename())" > ~/zonec
gcloud compute instances list --filter="name=vm2-vpc2-ncc" --format="value(zone.basename())" > ~/zone2
gcloud compute instances list --filter="name=vm1-vpc1-ncc" --format="value(networkInterfaces[0].networkIP)" > ~/vm1ip
head ~/project ~/region ~/sqlname ~/zonec ~/zone2 ~/vm1ip
gcloud sql instances list --format="table(name,region,state)"
```

You should see six values, none empty, and one Cloud SQL instance, RUNNABLE, in the same region as ~/region.

## Task 1. Create the hub

```bash
gcloud network-connectivity hubs create ncc-hub

```

You should see the hub path and ACTIVE.

## Task 2. Make both VPCs spokes

A VPC spoke exports its subnet routes to the hub, and every other spoke imports them. The exclude flag keeps one range private: it is not shared with the hub.

```bash
gcloud compute networks subnets list --network=vpc1-ncc
gcloud network-connectivity spokes linked-vpc-network create vpc1-spoke1 --hub=ncc-hub --vpc-network=vpc1-ncc --exclude-export-ranges=10.1.2.0/24 --global
gcloud network-connectivity spokes linked-vpc-network create vpc2-spoke2 --hub=ncc-hub --vpc-network=vpc2-ncc --exclude-export-ranges=10.3.3.0/24 --global
gcloud network-connectivity hubs route-tables routes list --hub=ncc-hub --route_table=default
```

You should see the vpc1 subnets first, then (after both spokes) the hub route table. Look for what is missing: the subnets inside 10.1.2.0/24 and 10.3.3.0/24 are not in the table. That is the exclude rule working.

Check my progress: Configure VPCs as an NCC spoke.

## Task 3. Verify the data path (not scored)

```bash
gcloud compute ssh vm2-vpc2-ncc --zone=`cat ~/zone2` --tunnel-through-iap --quiet --command="ping -c 5 `cat ~/vm1ip`" < /dev/null
```

You should see 5 packets transmitted, 5 received. vm2 is in VPC2 and vm1 in VPC1; with no peering between them, the hub is the only reason this works. If it shows 100% loss, wait a minute and run it again. To watch the packets arrive, do the lab's tcpdump step on vm1-vpc1-ncc from the console SSH button.

## Task 4. Private Service Connect to Cloud SQL

A PSC endpoint is an internal IP in your VPC that forwards to a service someone else publishes (here, the Cloud SQL instance's service attachment). The DNS record then gives that IP the name Cloud SQL expects.

Block 1 - reserve an IP and collect the Cloud SQL details:

```bash
gcloud compute addresses create cloudsql-psc --region=`cat ~/region` --subnet=vpc2-ncc-subnet1
gcloud compute addresses describe cloudsql-psc --region=`cat ~/region` --format="value(address)" > ~/pscip
gcloud sql instances describe `cat ~/sqlname` --format="value(pscServiceAttachmentLink)" > ~/sa
gcloud sql instances describe `cat ~/sqlname` --format="value(dnsName)" > ~/dnsname
rev ~/dnsname | cut -c2- | rev > ~/dnshost
head ~/pscip ~/sa ~/dnsname ~/dnshost
gcloud compute addresses list --filter="name=cloudsql-psc"
```

You should see an IP, a service attachment path, a DNS name ending in .sql.goog. (with the final dot), the same name without the final dot, and the address with status RESERVED.

Block 2 - create the endpoint:

```bash
gcloud compute forwarding-rules create cloudsql-psc-ep --address=cloudsql-psc --region=`cat ~/region` --network=vpc2-ncc --target-service-attachment=`cat ~/sa` --allow-psc-global-access
gcloud compute forwarding-rules describe cloudsql-psc-ep --region=`cat ~/region` --format="value(pscConnectionStatus)"
```

You should see ACCEPTED. If it is blank or PENDING, wait 20 seconds and run the second line again.

Block 3 - private DNS zone and record:

```bash
gcloud dns managed-zones create cloudsql-dns --description="DNS zone for the Cloud SQL instances" --dns-name=`cat ~/region`.sql.goog. --networks=vpc2-ncc --visibility=private
gcloud dns record-sets create `cat ~/dnsname` --type=A --rrdatas=`cat ~/pscip` --zone=cloudsql-dns
gcloud dns record-sets list --zone=cloudsql-dns --filter="type=A"
```

You should see one A record: the Cloud SQL DNS name pointing at your reserved IP.

Check my progress: Setup Private Service Connect.

## Task 5. Connect to Cloud SQL through the endpoint

The password is changeme (given by the lab). The first command creates the database; the second sends a SQL file into psql on the client VM.

```bash
cat > ~/company.sql <<'EOF'
CREATE TABLE employees (
    id SERIAL PRIMARY KEY,
    first VARCHAR(255) NOT NULL,
    last VARCHAR(255) NOT NULL,
    salary DECIMAL (10, 2)
);
INSERT INTO employees (first, last, salary) VALUES
    ('Max', 'Mustermann', 5000.00),
    ('Anna', 'Schmidt', 7000.00),
    ('Peter', 'Mayer', 6000.00);
SELECT * FROM employees;
EOF
gcloud compute ssh cloudsql-client --zone=`cat ~/zonec` --tunnel-through-iap --quiet --command="PGPASSWORD=changeme PGSSLMODE=disable psql -h `cat ~/dnshost` -U postgres -d postgres -c 'CREATE DATABASE company;'" < /dev/null
gcloud compute ssh cloudsql-client --zone=`cat ~/zonec` --tunnel-through-iap --quiet --command="PGPASSWORD=changeme PGSSLMODE=disable psql -h `cat ~/dnshost` -U postgres -d company" < ~/company.sql
```

You should see CREATE DATABASE, then CREATE TABLE, INSERT 0 3, and a table with Max, Anna and Peter (3 rows). The client VM reached Cloud SQL by name, through the private IP you reserved.

If you prefer the lab's interactive way, connect with the lab's own ssh command and use the name printed by cat ~/dnshost as the host.

Check my progress: Connect to Cloud SQL via Private Service Connect.
